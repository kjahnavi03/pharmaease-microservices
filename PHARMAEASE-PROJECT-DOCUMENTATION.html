📋 Project Overview

What is PharmaEase?

PharmaEase is a comprehensive online pharmacy platform built using Microservices Architecture. It allows customers to browse medicines, place orders, upload prescriptions, make payments, and track their orders. Administrators can manage medicines, approve prescriptions, update order statuses, and send notifications to customers.

🎯 Project Goals

  • Scalability: Each service can scale independently based on demand
  • Maintainability: Services are loosely coupled and can be developed/deployed independently
  • Resilience: Failure in one service doesn't bring down the entire system
  • Technology Diversity: Different services can use different technologies
  • Real-world Simulation: Mimics production-grade e-commerce systems

🏗️ Architecture Pattern

Microservices Architecture

The application is divided into 9 independent microservices, each responsible for a specific business capability. Services communicate via:

  • REST APIs (synchronous communication)
  • RabbitMQ (asynchronous messaging)
  • Feign Clients (inter-service communication)

🔗 Service Communication Patterns

1. Synchronous Communication (REST + Feign)

Used when: Immediate response is required

Example: Order Service → Catalog Service (Get medicine price)

@FeignClient(name = "catalog-service") public interface CatalogClient { @GetMapping("/api/catalog/medicines/{id}") MedicineDto getMedicineById(@PathVariable Long id); }

Advantages: Simple, immediate response, easy to debug

Disadvantages: Tight coupling, service dependency, blocking

2. Asynchronous Communication (RabbitMQ)

Used when: Fire-and-forget, non-critical operations

Example: Order Service → Notification Service (Send email)

// Publisher (Order Service) rabbitTemplate.convertAndSend("notification-exchange", "notification.order", notificationRequest); // Consumer (Notification Service) @RabbitListener(queues = "notification-queue") public void handleNotification(NotificationRequest req) { emailService.sendEmail(req.getTo(), req.getSubject(), req.getMessage()); }

Advantages: Loose coupling, non-blocking, resilient

Disadvantages: Eventual consistency, harder to debug

🔄 Complete Project Flow

1️⃣ User Registration & Login Flow

1. User visits http://localhost:4200
↓
2. Clicks "Register" → Fills form (name, email, password, phone)
↓
3. Frontend → POST /api/auth/signup → Gateway → Auth Service
↓
4. Auth Service: Hash password (BCrypt) → Save to auth_db
↓
5. User clicks "Login" → Enters email & password
↓
6. Frontend → POST /api/auth/login → Gateway → Auth Service
↓
7. Auth Service: Verify password → Generate JWT token
↓
8. Frontend stores JWT in localStorage → Redirects to Home

2️⃣ Browse Medicines Flow

1. User navigates to "Medicines" page
↓
2. Frontend → GET /api/catalog/medicines → Gateway → Catalog Service
↓
3. Catalog Service: Query catalog_db.medicines → Return list
↓
4. Frontend displays medicines with search, filter, pagination
↓
5. User clicks "Add to Cart" → Stored in CartService (in-memory)

3️⃣ Place Order Flow (Complete E2E)

1. User adds medicines to cart → Clicks "Checkout"
↓
2. If prescription required → Upload prescription image
↓
3. Frontend → POST /api/catalog/prescriptions → Catalog Service
↓
4. Prescription saved with status=PENDING
↓
5. User enters delivery address → Clicks "Place Order"
↓
6. Frontend → POST /api/orders → Gateway → Order Service
↓
7. Order Service → Feign call to Catalog Service (get medicine prices)
↓
8. Order Service: Calculate total → Save order to order_db
↓
9. If prescription required → Order status = AWAITING_PRESCRIPTION
Else → Order status = PENDING
↓
10. Order Service → Publish to RabbitMQ (ORDER_PLACED event)
↓
11. Notification Service → Consumes event → Sends email
↓
12. Frontend redirects to Payment page

4️⃣ Admin Approves Prescription Flow

1. Admin logs in → Navigates to "Prescriptions"
↓
2. Frontend → GET /api/admin/prescriptions → Admin Service
↓
3. Admin Service → Feign call to Catalog Service (get prescriptions)
↓
4. Admin reviews prescription image → Clicks "Approve"
↓
5. Frontend → PUT /api/admin/prescriptions/{id}/approve
↓
6. Admin Service → Updates prescription status=APPROVED
↓
7. Admin Service → Feign call to Order Service (approve orders)
↓
8. Order Service: Update order status AWAITING_PRESCRIPTION → PENDING
↓
9. Notification sent to customer: "Prescription approved!"

5️⃣ Payment Flow

1. User on Payment page → Selects payment method (CARD/UPI/CASH)
↓
2. Frontend → POST /api/payments → Gateway → Payment Service
↓
3. Payment Service: Generate transaction ID → Save to payment_db
↓
4. Payment Service → Feign call to Order Service (update status to PAID)
↓
5. Order Service: Decrement stock via Catalog Service
↓
6. Notification sent: "Payment successful!"
↓
7. Frontend redirects to "My Orders"

6️⃣ Order Status Update Flow

1. Admin → "Orders" page → Selects order
↓
2. Admin changes status: PAID → PACKED → SHIPPED → DELIVERED
↓
3. Frontend → PUT /api/admin/orders/{id}/status → Admin Service
↓
4. Admin Service → Feign call to Order Service (update status)
↓
5. Order Service: Update order → Publish notification event
↓
6. Customer receives email: "Your order has been shipped!"

7️⃣ Notification Flow (Asynchronous)

1. Any service publishes event to RabbitMQ
↓
2. RabbitMQ stores message in notification-queue
↓
3. Notification Service consumes message (@RabbitListener)
↓
4. EmailService checks if MAIL_ENABLED=true
↓
5. If enabled → Send email via Gmail SMTP
If disabled → Log to console
↓
6. Customer receives email notification

🔐 Security Implementation

JWT (JSON Web Token) Authentication

How it works:

  1. User logs in with email/password
  2. Auth Service verifies credentials → Generates JWT token
  3. Token contains: email, roles, expiry (24 hours)
  4. Frontend stores token in localStorage
  5. Every API request includes: Authorization: Bearer <token>
  6. Gateway validates token before routing to services
// JWT Token Structure { "sub": "user@example.com", // Subject (email) "roles": ["CUSTOMER"], // User roles "iat": 1714838400, // Issued at "exp": 1714924800 // Expires at } // Signed with HMAC-SHA256 using secret key

Why JWT?

  • ✅ Stateless - No session storage needed
  • ✅ Scalable - Works across multiple servers
  • ✅ Secure - Signed and optionally encrypted
  • ✅ Self-contained - Contains all user info

Alternative: Session-based auth (requires Redis/database for session storage)

🐰 RabbitMQ Messaging Pattern

Publisher (Order Service)

@Component public class NotificationPublisher { private final RabbitTemplate rabbitTemplate; public void publish(NotificationRequest req) { rabbitTemplate.convertAndSend( "notification-exchange", "notification.order", req ); } }

Consumer (Notification Service)

@Component public class NotificationConsumer { @RabbitListener(queues = "notification-queue") public void handleNotification(NotificationRequest req) { emailService.sendEmail( req.getTo(), req.getSubject(), req.getMessage() ); } }

Why RabbitMQ?

  • Asynchronous - Non-blocking operations
  • Reliable - Message persistence, acknowledgments
  • Decoupled - Services don't need to know each other
  • Scalable - Multiple consumers can process messages

Alternative: Apache Kafka (better for high-throughput event streaming)

1️⃣ Eureka Server (Port 8761)

📌 Purpose

Service Registry and Discovery - Central registry where all microservices register themselves

🎯 What It Does

  • Services register on startup with their name, IP, and port
  • Provides service discovery - Gateway can find services by name
  • Health checks - Detects when services go down

Problems:

  • Hardcode service URLs everywhere (http://localhost:9091)
  • Manual load balancing
  • No auto-scaling support
  • Service failures not detected automatically

  • Consul: Service discovery + key-value store
  • Kubernetes Service Discovery: Built-in if using K8s
  • AWS Cloud Map: AWS-native service discovery

🎤 Interview Questions

Q: How does Eureka handle service failures?

Answer: Eureka uses heartbeat mechanism. Each service sends heartbeat every 30 seconds. If Eureka doesn't receive heartbeat for 90 seconds, it marks the service as DOWN and removes it from registry. Gateway won't route requests to failed services.

Q: What is self-preservation mode in Eureka?

Answer: When network partition occurs and many services stop sending heartbeats, Eureka enters self-preservation mode. It assumes it's a network issue, not service failures, and keeps all registrations. This prevents mass de-registration during network problems.

🎤 Interview Questions

Q: What's the difference between API Gateway and Load Balancer?

Answer:

  • Load Balancer: Distributes traffic across multiple instances of SAME service (Layer 4/7)
  • API Gateway: Routes to DIFFERENT services based on URL path, handles auth, rate limiting (Layer 7 only)

Gateway can include load balancing, but load balancer can't do routing/auth.

Q: How does Gateway handle service failures?

Answer: Gateway uses Circuit Breaker pattern (Resilience4j). If a service fails repeatedly:

  1. Closed: Normal operation
  2. Open: After threshold failures, stop calling service, return fallback
  3. Half-Open: After timeout, try again. If success → Closed, if fail → Open

4️⃣ Auth Service (Port 9091)

📌 Purpose

Authentication & Authorization - Manages user accounts and JWT tokens

🎯 What It Does

  • User registration with password hashing (BCrypt)
  • User login with JWT token generation
  • Role-based access control (CUSTOMER, ADMIN)
  • Admin token validation for admin registration

💻 Key Implementation

// Password Hashing String hashedPassword = passwordEncoder.encode(plainPassword); // BCrypt: $2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy // JWT Generation String token = Jwts.builder() .setSubject(email) .claim("roles", roles) .setIssuedAt(new Date()) .setExpiration(new Date(System.currentTimeMillis() + 86400000)) // 24h .signWith(SignatureAlgorithm.HS256, secretKey) .compact();

🗄️ Database Schema

-- users table CREATE TABLE users ( id BIGINT PRIMARY KEY AUTO_INCREMENT, first_name VARCHAR(255) NOT NULL, last_name VARCHAR(255) NOT NULL, email VARCHAR(255) UNIQUE NOT NULL, password VARCHAR(255) NOT NULL, -- BCrypt hash contact_number VARCHAR(20) ); -- user_roles table (many-to-many) CREATE TABLE user_roles ( user_id BIGINT, role VARCHAR(50), -- CUSTOMER, ADMIN FOREIGN KEY (user_id) REFERENCES users(id) );

❓ Why BCrypt for Password Hashing?

  • Slow by design: Makes brute-force attacks impractical
  • Salted: Each password has unique salt (prevents rainbow tables)
  • Adaptive: Can increase cost factor as hardware improves
  • One-way: Cannot decrypt, only verify

🎤 Interview Questions

Q: Why JWT instead of session-based authentication?

Answer:

Aspect JWT (Stateless) Session (Stateful)

Q: How do you handle concurrent stock updates?

@Transactional public OrderResponse placeOrder(OrderRequest req, String email) { Order order = new Order(); order.setCustomerId(req.getCustomerId()); order.setCustomerEmail(email); boolean hasPrescriptionItem = false; BigDecimal total = BigDecimal.ZERO; for (OrderItemRequest itemReq : req.getItems()) { // Feign call to Catalog Service MedicineDto medicine = catalogClient.getMedicineById(itemReq.getMedicineId()); if (medicine.isRequiresPrescription()) { hasPrescriptionItem = true; } OrderItem item = new OrderItem(); item.setMedicineId(medicine.getId()); item.setMedicineName(medicine.getName()); // Snapshot item.setQuantity(itemReq.getQuantity()); item.setUnitPrice(medicine.getPrice()); // Snapshot order.getItems().add(item); total = total.add(medicine.getPrice().multiply( BigDecimal.valueOf(itemReq.getQuantity()) )); } order.setTotalAmount(total); if (hasPrescriptionItem) { order.setStatus(OrderStatus.AWAITING_PRESCRIPTION); order.setPrescriptionId(req.getPrescriptionId()); } else { order.setStatus(OrderStatus.PENDING); } Order saved = orderRepo.save(order); // Publish notification event notificationPublisher.publish(new NotificationRequest( email, "Order Placed - #" + saved.getId(), "Your order has been placed. Total: Rs." + saved.getTotalAmount(), "ORDER_PLACED" )); return toResponse(saved); }

Reason: Historical accuracy

  • Medicine may be deleted from catalog

Q: What if Catalog Service is down when placing order?

Currently, order placement fails immediately. Better approach: Circuit Breaker + Fallback.

💻 Email Service

@Service public class EmailService { @Value("${notification.email.enabled:false}") private boolean emailEnabled; @Value("${notification.email.from}") private String fromAddress; private final JavaMailSender mailSender; public void sendEmail(String to, String subject, String body) { if (!emailEnabled) { log.info("[EMAIL-DISABLED] to={} subject={}", to, subject); return; } try { SimpleMailMessage message = new SimpleMailMessage(); message.setFrom(fromAddress); message.setTo(to); message.setSubject(subject); message.setText(body); mailSender.send(message); log.info("[EMAIL-SENT] to={}", to); } catch (MailException ex) { log.error("[EMAIL-FAILED] to={} error={}", to, ex.getMessage()); } } }

@Component public class NotificationConsumer { private final EmailService emailService; @RabbitListener(queues = "notification-queue") public void handleNotification(NotificationRequest req) { log.info("[NOTIFICATION] Received: type={} to={}", req.getType(), req.getTo()); emailService.sendEmail( req.getTo(), req.getSubject(), req.getMessage() ); } }

❓ Why Asynchronous Notifications?

  • Non-blocking: Order placement doesn't wait for email
  • Resilient: If email fails, order still succeeds
  • Scalable: Multiple consumers can process notifications
  • Retry: RabbitMQ can retry failed messages
  • Decoupled: Services don't depend on notification service

🎤 Interview Questions

Q: What if RabbitMQ is down?

Answer:

  • Publisher: Message publish fails, but order succeeds (non-critical)
  • Solution 1: Catch exception, log to database, retry later
  • Solution 2: Use RabbitMQ cluster for high availability
  • Solution 3: Fallback to direct email sending
Q: How do you prevent duplicate notifications?

Answer:

  1. Idempotency: Store sent notification IDs in database/cache
  2. Message Deduplication: RabbitMQ message ID
  3. Consumer Acknowledgment: Manual ack after successful send
@RabbitListener(queues = "notification-queue", ackMode = "MANUAL") public void handleNotification(NotificationRequest req, Channel channel, @Header(AmqpHeaders.DELIVERY_TAG) long tag) { try { emailService.sendEmail(req.getTo(), req.getSubject(), req.getMessage()); channel.basicAck(tag, false); // Acknowledge success } catch (Exception e) { channel.basicNack(tag, false, true); // Requeue on failure } }

🎤 Comprehensive Interview Questions & Answers

🏗️ Architecture & Design Questions

Q1: Why did you choose Microservices over Monolithic architecture?

Answer:

Aspect Monolithic Microservices (Our Choice)
Deployment Deploy entire app ✅ Deploy individual services
Scaling Scale entire app ✅ Scale only needed services
Technology Single tech stack ✅ Different tech per service
Failure One bug crashes all ✅ Isolated failures
Team Single large team ✅ Small independent teams

Trade-offs: Microservices add complexity (distributed systems, network latency, data consistency)

Q2: How do you handle distributed transactions across services?

Answer: We use Eventual Consistency with Saga Pattern

Example: Order Placement

  1. Order Service: Create order (status=PENDING)
  2. Payment Service: Process payment
  3. If payment succeeds → Update order (status=PAID)
  4. If payment fails → Cancel order (compensating transaction)

Alternatives:

  • 2PC (Two-Phase Commit): Distributed transaction, but slow and blocking
  • Saga Pattern: Sequence of local transactions with compensations
  • Event Sourcing: Store events, rebuild state from events
Q3: How do you ensure data consistency across services?

Answer:

  1. Database Per Service: Each service owns its data
  2. API Calls: Services communicate via APIs (not direct DB access)
  3. Event-Driven: Publish events when data changes (RabbitMQ)
  4. Eventual Consistency: Accept temporary inconsistency
  5. Idempotency: Same request produces same result

Example: When order is placed, stock is decremented asynchronously. Brief window where order exists but stock not yet decremented.

Q4: What happens if one microservice is down?

Answer: Depends on the service:

  • Eureka Down: Services can't discover each other → Use cached registry
  • Gateway Down: No requests reach services → Use load balancer with multiple gateways
  • Auth Service Down: Can't login → Use cached JWT tokens (existing users work)
  • Catalog Service Down: Can't browse medicines → Use Circuit Breaker + Cache
  • Notification Service Down: No emails sent → Non-critical, order still succeeds

Resilience Patterns:

  1. Circuit Breaker: Stop calling failed service
  2. Retry: Retry with exponential backoff
  3. Fallback: Return cached/default data
  4. Timeout: Don't wait forever

🔐 Security Questions

Q5: How do you secure microservices?

Answer: Multiple layers:

  1. Authentication (JWT):
    • User logs in → Auth Service generates JWT
    • Frontend includes JWT in every request
    • Gateway validates JWT before routing
  2. Authorization (Roles):
    • JWT contains user roles (CUSTOMER, ADMIN)
    • Services check roles before allowing operations
    • Example: Only ADMIN can approve prescriptions
  3. HTTPS: Encrypt data in transit
  4. API Gateway: Single entry point, easier to secure
  5. Rate Limiting: Prevent DDoS attacks
  6. Input Validation: Prevent SQL injection, XSS
Q6: How do you prevent SQL Injection?

Answer: We use Spring Data JPA with Parameterized Queries

// ❌ BAD: String concatenation (vulnerable) String query = "SELECT * FROM users WHERE email = '" + email + "'"; // ✅ GOOD: Parameterized query (safe) @Query("SELECT u FROM User u WHERE u.email = :email") User findByEmail(@Param("email") String email);

JPA automatically escapes parameters, preventing injection.

Q7: How do you store passwords securely?

Answer: We use BCrypt hashing

  • Never store plain text: Database breach doesn't expose passwords
  • One-way hash: Cannot decrypt, only verify
  • Salted: Each password has unique salt (prevents rainbow tables)
  • Slow by design: Makes brute-force impractical
// Registration String hashed = passwordEncoder.encode("password123"); // Result: $2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy // Login boolean matches = passwordEncoder.matches("password123", hashed); // true

📊 Database Questions

Q8: Why separate databases for each service?

Answer: Database Per Service Pattern

Benefits:

  • Loose Coupling: Services don't share database schema
  • Independent Scaling: Scale database per service needs
  • Technology Diversity: Can use different databases (MySQL, MongoDB, Redis)
  • Fault Isolation: Database failure affects only one service
  • Team Autonomy: Teams can change schema without coordination

Challenges:

  • No foreign keys across services
  • No JOIN queries across services
  • Data duplication (denormalization)
  • Eventual consistency
Q9: How do you handle database migrations?

Answer: We use Hibernate DDL Auto (development) and Flyway/Liquibase (production)

# Development (auto-create tables) spring: jpa: hibernate: ddl-auto: update # create, update, validate, none # Production (versioned migrations) # Use Flyway: V1__create_users.sql, V2__add_roles.sql

Best Practice: Never use ddl-auto: update in production!

Q10: How do you optimize database queries?

Answer: Multiple strategies:

  1. Indexing: Create indexes on frequently queried columns
    CREATE INDEX idx_email ON users(email);
  2. Eager vs Lazy Loading:
    @ManyToOne(fetch = FetchType.EAGER) // Load immediately @OneToMany(fetch = FetchType.LAZY) // Load on access
  3. Pagination: Don't load all records
    Page<Medicine> findAll(Pageable pageable);
  4. Caching: Cache frequently accessed data (Redis)
  5. Query Optimization: Use EXPLAIN to analyze queries
